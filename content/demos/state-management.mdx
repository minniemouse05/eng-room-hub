# React State Management Patterns

Choosing the right state management approach is crucial for building maintainable React applications. This guide covers the spectrum from simple to complex.

## The State Management Spectrum

From simplest to most complex:

1. **Local state** (`useState`) - Component-specific data
2. **Lifted state** - Shared between siblings via parent
3. **Context** - Shared across distant components
4. **External stores** - Complex, global state

## 1. Local State with useState

Use for data that belongs to a single component:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      Count: {count}
    </button>
  );
}
```

### When to Use

- Form inputs
- Toggle states (open/closed)
- Local UI state (selected tab)
- Data that doesn't need to be shared

## 2. Lifted State

Share state between siblings by lifting to their common parent:

```tsx
function Parent() {
  const [selectedId, setSelectedId] = useState<string | null>(null);

  return (
    <div>
      <Sidebar selectedId={selectedId} onSelect={setSelectedId} />
      <MainContent selectedId={selectedId} />
    </div>
  );
}
```

### When to Use

- Two or three components need the same data
- Components are close in the tree
- State updates don't cause excessive re-renders

## 3. useReducer for Complex State

When state logic becomes complex:

```tsx
type State = {
  items: Item[];
  loading: boolean;
  error: string | null;
};

type Action =
  | { type: 'FETCH_START' }
  | { type: 'FETCH_SUCCESS'; payload: Item[] }
  | { type: 'FETCH_ERROR'; payload: string }
  | { type: 'ADD_ITEM'; payload: Item }
  | { type: 'REMOVE_ITEM'; payload: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'FETCH_START':
      return { ...state, loading: true, error: null };
    case 'FETCH_SUCCESS':
      return { ...state, loading: false, items: action.payload };
    case 'FETCH_ERROR':
      return { ...state, loading: false, error: action.payload };
    case 'ADD_ITEM':
      return { ...state, items: [...state.items, action.payload] };
    case 'REMOVE_ITEM':
      return {
        ...state,
        items: state.items.filter(item => item.id !== action.payload)
      };
    default:
      return state;
  }
}

function ItemList() {
  const [state, dispatch] = useReducer(reducer, {
    items: [],
    loading: false,
    error: null
  });

  // ...
}
```

### When to Use

- Multiple sub-values that change together
- Next state depends on previous state
- Complex state update logic
- You want predictable state transitions

## 4. Context for Shared State

Share state across many components without prop drilling:

```tsx
// Create context
const AuthContext = createContext<AuthContextValue | null>(null);

// Provider component
function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const login = async (credentials: Credentials) => {
    const user = await authApi.login(credentials);
    setUser(user);
  };

  const logout = () => {
    authApi.logout();
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom hook
function useAuth() {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth must be used within AuthProvider');
  }
  return context;
}

// Usage
function ProfileButton() {
  const { user, logout } = useAuth();
  // ...
}
```

### Context Performance Considerations

```tsx
// Problem: All consumers re-render on any state change
const AppContext = createContext({ user, theme, settings });

// Solution: Split into multiple contexts
const UserContext = createContext(user);
const ThemeContext = createContext(theme);
const SettingsContext = createContext(settings);
```

### When to Use

- Theme, authentication, locale settings
- Data needed in many places
- Avoiding deep prop drilling
- Relatively stable data (not rapidly changing)

## 5. External State Libraries

For complex applications, consider external solutions:

### Zustand (Simple)

```tsx
import { create } from 'zustand';

const useStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
}));

function Counter() {
  const { count, increment } = useStore();
  return <button onClick={increment}>{count}</button>;
}
```

### When to Use External Stores

- Large application with complex state
- State shared across many features
- Need for advanced features (persistence, middleware)
- Team prefers specific patterns (Redux, MobX)

## Decision Framework

Ask these questions:

1. **Does only one component need this?** → `useState`
2. **Do siblings need it?** → Lift state to parent
3. **Is the logic complex?** → `useReducer`
4. **Do distant components need it?** → Context
5. **Is it app-wide with complex interactions?** → External store

## Best Practices

1. **Start simple** - Begin with local state, add complexity only when needed
2. **Colocate state** - Keep state as close to where it's used as possible
3. **Normalize data** - Avoid deeply nested state structures
4. **Derive when possible** - Calculate values from existing state instead of storing
5. **Use selectors** - Prevent unnecessary re-renders

```tsx
// Deriving state instead of storing
function ProductList({ products }) {
  const totalPrice = useMemo(
    () => products.reduce((sum, p) => sum + p.price, 0),
    [products]
  );
  // Don't store totalPrice in state!
}
```
